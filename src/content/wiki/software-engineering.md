Software engineering is not synonymous with writing code. The distinction matters more now than it did a decade ago, and a significant cluster of recent sources circles back to it from different angles.

The gap between algorithm interviews and actual engineering work is one symptom. [Learn Algorithms for Interviews, Forget Them for Work](/reading/2026-04/2026-04-30t155134-learn-algorithms-for-interviews-forget-them-for-work) argues that whiteboard problems test a narrow, trainable skill that weakly correlates with production performance. Real engineering means reading tradeoffs, shipping incrementally, and building systems that handle messy, unbounded real-world inputs. The hiring process optimizes for a proxy that keeps drifting from the thing being proxied, and [The systemic decay of tech hiring](/reading/2026-06/2026-06-22t182141-the-systemic-decay-of-tech-hiring) traces how that drift compounds: error asymmetry pushes interviewers toward ever-harder tests, shared pools destroy accountability, and candidates overfit to the process via Goodhart's Law.

Once hired, engineers face a different gap: what they know versus what they can articulate. [Why Senior Developers Fail to Communicate Their Expertise](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) frames it as a vocabulary mismatch — senior engineers think in terms of complexity management while the rest of the business thinks in terms of uncertainty reduction. [The Tacit Dimension](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you) goes deeper, drawing on Polanyi to argue that the most valuable engineering expertise — pattern recognition, unwritten conventions, design intuition — is structurally inaccessible to documentation or AI tools and can only be transmitted through apprenticeship.

Principles like the Single Responsibility Principle suffer the same translation problem. [Single Responsibility, the Distorted Principle](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) argues SRP is widely misread as "do only one thing" when it actually means cohesive grouping under a single accountable responsibility — and that over-granularizing classes violates the cognitive simplicity SRP was meant to provide. Similarly, [AI Likes Deep Modules](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) contends that small interfaces hiding large implementations reduce complexity for both humans and LLMs, contrasting shallow versus deep design with concrete Go examples.

Module design, test design, and code review all carry the same underlying tension: implementation details versus stable contracts. [Designing Playwright Tests That Survive UI Refactors](/reading/2026-05/2026-05-05t135218-designing-playwright-tests-that-survive-ui-refactors) shows that test suites break not from bad selector choices alone but from coupling to DOM structure rather than semantic roles. [Code Smells when you get AI to write your Frontend Tests](/reading/2026-06/2026-06-22t185420-code-smells-when-you-get-ai-to-write-your-frontend-tests) documents how AI-generated tests compound this: over-mocking, testing only happy paths, and writing tests to match a buggy implementation rather than intended behavior.

The introduction of AI tooling has sharpened every existing debate about craft versus speed. [Agentic Coding is a Trap](/reading/2026-04/2026-04-27t145041-agentic-coding-is-a-trap) argues that full agentic workflows accelerate skill atrophy and invert developer priorities toward speed over understanding. [The Perils of "AI" to the Software Engineering Profession](/reading/2026-05/2026-05-14t223612-the-perils-of-ai-to-the-software-engineering-profession) calls shipping unreviewed AI-generated code categorically incompatible with safety-critical systems. [When Code Is Cheap, Does Quality Still Matter?](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter) answers yes: AI lowers the cost of producing code but not the cost of owning it, and LLMs can generate polished technical debt faster than any individual engineer ever could.

Not every source is pessimistic. [The bottleneck was never the code](/reading/2026-05/2026-05-06t110728-the-bottleneck-was-never-the-code) reframes the debate: coding agents make individual code-writing cheap, but the real bottleneck was always organizational — shared context, specification clarity, and management coherence — and agents amplify whatever alignment or misalignment an organization already has. [Slow Mode](/reading/2026-05/2026-05-19t193626-slow-mode) proposes keeping the human programmer involved at every agent step to trade short-term productivity for genuine learning and long-term code ownership. [Use Your Brain: Engineering Standards in the Age of LLMs](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms) calls for strong CI/CD and code ownership as the mechanism for using AI as an amplifier rather than a crutch.

Below the level of tooling choices, production reality imposes its own constraints. [The Unwritten Laws of Software Engineering](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) distills hard-won rules from real incidents: roll back before debugging, treat every external dependency as a future outage. [When Impressive Performance Gains Do Not Matter](/reading/2026-06/2026-06-30t185207-when-impressive-performance-gains-do-not-matter) shows that attention thresholds, discrete capacity increments, and pipeline backpressure explain why even order-of-magnitude improvements often fail to change outcomes. [Approaching zero bugs?](/reading/2026-05/2026-05-02t094735-approaching-zero-bugs) uses curl's vulnerability data to argue there is no measurable sign yet that AI-assisted static analysis is closing the latent bug gap.

Version control tooling is also in motion. [Reviewing Large Changes with Jujutsu](/reading/2026-05/2026-05-31t164252-reviewing-large-changes-with-jujutsu) describes a workflow using Jujutsu's conflict-as-first-class-object model to persist review progress in version control, and [the Jujutsu repository itself](/reading/2026-05/2026-05-31t164554-jj-vcsjj) offers a Git-compatible alternative that auto-commits the working copy and rebases descendants automatically. Meanwhile, [GitHub is Sinking](/reading/2026-05/2026-05-10t205349-github-is-sinking) and [If I Could Make My Own GitHub](/reading/2026-06/2026-06-23t231556-if-i-could-make-my-own-github) both argue that the dominant forge has declined and that the tooling layer around code hosting deserves the same engineering scrutiny as the code itself.

Across all of these, the recurring theme is judgment: knowing when a performance gain matters, when a test is actually testing behavior, when a refactor simplifies rather than fragments, and when AI output needs to be owned rather than accepted. That judgment is what separates software engineering from code generation, and it is the thing most at risk when speed becomes the primary optimization target.
