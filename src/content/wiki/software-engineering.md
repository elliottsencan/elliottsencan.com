Software engineering is not a single discipline but a layered set of concerns: writing code that works, structuring it so it stays maintainable, shipping it safely, and building the teams and processes that sustain all of the above. The sources tagged here span all those layers, and a through-line connects most of them: AI tooling is changing the cost structure of producing code without changing what it costs to own it.

The ownership problem is argued most directly in ["When Code Is Cheap, Does Quality Still Matter?"](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter), which notes that LLMs can generate polished, well-formatted technical debt faster than any individual engineer. The concern isn't AI in the abstract but what happens when speed is decoupled from understanding. Lars Faye makes the same argument from a skill-atrophy angle in ["Agentic Coding is a Trap"](/reading/2026-04/2026-04-27t145041-agentic-coding-is-a-trap), arguing that full agentic workflows invert developer priorities toward speed and create vendor dependency, and that LLMs belong as delegation tools rather than primary authors. Abednego Gomes extends this to safety-critical domains in ["The Perils of AI to the Software Engineering Profession"](/reading/2026-05/2026-05-14t223612-the-perils-of-ai-to-the-software-engineering-profession), calling vibe coding categorically incompatible with systems where failures hurt people. Anton Zaides captures the internal organizational split in ["The Software Engineering War"](/reading/2026-07/2026-07-07t170607-the-software-engineering-war): builders want to ship fast with AI; keepers insist on quality; and where you land depends heavily on who's in the room.

The cognitive ownership problem has a structural form too. The ["Tacit Dimension"](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you) argues, drawing on Michael Polanyi, that the most valuable engineering expertise — pattern recognition, design intuition, unwritten conventions — is structurally inaccessible to AI and can only be transmitted through apprenticeship. Paolo Galeone frames this as a "custodian" mindset risk in ["Use Your Brain"](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms), arguing for strong CI/CD and code ownership as amplifiers rather than replacements for judgment. The ["I Don't Know, Claude Wrote This" Pandemic](/reading/2026-08/2026-08-31t131721-the-i-dont-know-claude-wrote-this-pandemic) names the outcome directly: surrendering cognitive ownership of code.

Process and tooling questions run alongside the AI debate. ["The Unwritten Laws of Software Engineering"](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) distills production hard-won rules — roll back before debugging, treat every external dependency as a future outage. ["What CI Actually Looks Like at a 100-Person Team"](/reading/2026-04/2026-04-30t195531-what-ci-actually-looks-like-at-a-100-person-team) shows how AI triage agents at PostHog's scale handle 575K weekly CI jobs, tracing flaky tests and opening fix PRs automatically. ["Designing Playwright Tests That Survive UI Refactors"](/reading/2026-05/2026-05-05t135218-designing-playwright-tests-that-survive-ui-refactors) and ["Code Smells When You Get AI to Write Your Frontend Tests"](/reading/2026-06/2026-06-22t185420-code-smells-when-you-get-ai-to-write-your-frontend-tests) address testing quality from complementary angles: semantic selectors resist refactors; AI-generated tests tend toward over-mocking and happy-path-only coverage.

Module and component design concerns appear in several sources. ["AI Likes Deep Modules"](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) argues that small interfaces hiding large implementations reduce complexity for humans and LLMs alike. ["Single Responsibility, the Distorted Principle"](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) corrects the common misreading of SRP as "do one thing" — it means cohesive grouping under a single accountable responsibility, not over-granularization. ["A Better Way to Build Angular Components"](/reading/2026-04/2026-04-30t232001-a-better-way-to-build-angular-components-from-inputs-to) applies this to component design, recommending the Composite Components pattern over input-bloated monoliths.

Version control, code review, and codebase navigation get practical treatment. ["Reviewing Large Changes with Jujutsu"](/reading/2026-05/2026-05-31t164252-reviewing-large-changes-with-jujutsu) describes a structured jj-based workflow for reviewing large PRs incrementally. ["The Git Commands I Run Before Reading Any Code"](/reading/2026-06/2026-06-18t024208-the-git-commands-i-run-before-reading-any-code) and ["How I Audit a Legacy Rails Codebase"](/reading/2026-06/2026-06-18t090801-how-i-audit-a-legacy-rails-codebase-in-the-first-week) both argue for reading history and stakeholder fears before reading code. Supply chain security sits adjacent to code review: [the Ars Technica investigation](/reading/2026-04/2026-04-30t231634-supply-chain-attack-using-invisible-code-hits-github-and) documents 151 malicious npm packages encoding payloads in invisible Unicode characters that evade both human review and static analysis.

The hiring and communication failures that compound all of the above get their own treatments. ["Learn Algorithms for Interviews, Forget Them for Work"](/reading/2026-04/2026-04-30t155134-learn-algorithms-for-interviews-forget-them-for-work) argues that interview processes optimize for a narrow trainable skill that weakly correlates with production performance. ["The Systemic Decay of Tech Hiring"](/reading/2026-06/2026-06-22t182141-the-systemic-decay-of-tech-hiring) traces how error asymmetry and Goodhart's Law compound into dysfunctional interview loops. ["Why Senior Developers Fail to Communicate Their Expertise"](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) locates the gap not in AI but in the mismatch between engineering vocabulary (complexity management) and business vocabulary (uncertainty reduction). Poor onboarding compounds all of it: ["Your Onboarding Is a Hazing Ritual"](/reading/2026-05/2026-05-08t112608-your-onboarding-is-a-hazing-ritual-and-you-call-it-agile) describes how agile framing conceals dysfunction that sets new hires up to fail.

What holds these threads together is that software engineering's central problems — quality, knowledge transfer, process, judgment — are not solved by cheaper code generation. They may be sharpened by it.
