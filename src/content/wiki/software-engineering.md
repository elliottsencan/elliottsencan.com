Software engineering resists clean definition, and the sources gathered here make that resistance plain. The discipline encompasses everything from low-level performance optimization to organizational onboarding design, from version control workflows to the philosophy of what it means to know something about code.

One thread running through many sources is the gap between what interviews test and what production work actually demands. [Fagner Brack](/reading/2026-04/2026-04-30t155134-learn-algorithms-for-interviews-forget-them-for-work) argues that algorithm interviews measure a narrow, trainable skill that weakly correlates with real engineering ability — which involves reading tradeoffs, shipping incrementally, and handling unbounded real-world inputs. A related problem surfaces in hiring itself: [Vladimir Klepov](/reading/2026-06/2026-06-22t182141-the-systemic-decay-of-tech-hiring) traces how error asymmetry and shared interviewer pools have made technical interviews progressively more dysfunctional, with candidates and interviewers both overfitting to the process via Goodhart's Law.

Design principles get similar scrutiny. [Henrique Teixeira](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) argues that the Single Responsibility Principle is routinely misread as "do only one thing" when it actually means cohesive grouping under a single accountable responsibility — and that over-granularizing classes produces the cognitive fragmentation SRP was meant to prevent. [Go Monk](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) makes a complementary point through the lens of module design: small interfaces hiding large implementations reduce complexity for both humans and LLMs, contrasting with shallow modules that expose implementation noise.

Code quality and what it means to own code run through several essays. [Yusuf Aytas](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter) puts it plainly: AI lowers the cost of producing code but not the cost of owning it. LLMs can generate polished technical debt faster than any individual engineer. [Anton Zaides](/reading/2026-08/2026-08-31t131721-the-i-dont-know-claude-wrote-this-pandemic) sharpens this into a warning about cognitive ownership — engineers who let AI write code without understanding it surrender the ability to maintain or reason about it. Paolo Galeone [makes the same point](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms) through engineering standards: strong CI/CD and code ownership are the line between using AI as an amplifier and becoming its custodian.

The production systems perspective comes from [Sam Alba's account](/reading/2026-04/2026-04-30t195531-what-ci-actually-looks-like-at-a-100-person-team) of CI at PostHog's scale, where 575,000 weekly jobs and 33 million test executions make manual triage impossible. At that scale, an AI agent ingests billions of log lines and opens fix PRs automatically — not because engineering judgment is gone, but because scale forces delegation. [Anton Zaides](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) distills complementary operational wisdom: roll back before debugging, treat every external dependency as a future outage.

Security is part of engineering craft whether treated as such or not. [Dan Goodin](/reading/2026-04/2026-04-30t231634-supply-chain-attack-using-invisible-code-hits-github-and) documents a supply-chain attack that encoded payloads in invisible Unicode variation-selector characters, invisible to reviewers and static analysis but executable at runtime — a reminder that the threat surface includes what tools cannot see. [Emphere's testing approach](/reading/2026-06/2026-06-11t024225-testing-a-security-tool-like-it-can-hurt-people) for their container security tool takes this seriously: red runs that prove the system fails loudly when it overclaims certainty are as important as green runs.

The organizational dimension of software engineering is as contested as the technical one. [DHg](/reading/2026-05/2026-05-08t112608-your-onboarding-is-a-hazing-ritual-and-you-call-it-agile) argues that poor onboarding disguised as agile process systematically sets new hires up to fail while making the dysfunction invisible. [Tuhin Nair](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) identifies a different organizational gap: senior developers communicate in terms of complexity management while the rest of the business thinks in terms of uncertainty reduction, and bridging that gap is the real challenge of software expertise. [cekrem](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you) extends this through Michael Polanyi's philosophy of tacit knowledge, arguing that the most valuable engineering expertise — pattern recognition, design intuition, unwritten conventions — is structurally inaccessible to AI and can only be transmitted through apprenticeship.

Tooling choices shape what engineering looks like in practice. [Ben Gesoff](/reading/2026-05/2026-05-31t164252-reviewing-large-changes-with-jujutsu) shows how Jujutsu's first-class conflict objects and automatic descendant rebasing enable a review workflow that persists progress in version control rather than in cognitive working memory. [Christian Hofstede-Kuhn](/reading/2026-04/2026-04-30t231815-shell-tricks-that-actually-make-life-easier-and-save-your) makes the equivalent case for the shell: underused Readline bindings and script safety flags reduce the friction of everyday work. [Ally Piechowski](/reading/2026-06/2026-06-18t024208-the-git-commands-i-run-before-reading-any-code) demonstrates that git log itself is a diagnostic tool — churn hotspots, bus factor, and bug clusters are readable from commit history before a single source file is opened.

The debate about AI's role in engineering sits at the intersection of all of this. [Lars Faye](/reading/2026-04/2026-04-27t145041-agentic-coding-is-a-trap) warns that full agentic workflows accelerate skill atrophy and invert developer priorities toward speed over understanding. [Armin Ronacher](/reading/2026-06/2026-06-23t161552-the-coming-loop) notes that harness loops orchestrating coding agents risk producing codebases that require machine participation to maintain. [Dex Horthy](/reading/2026-07/2026-07-23t215330-humanlayeradvanced-context-engineering-for-coding-agents) goes further, arguing that lights-off software factories fail because LLMs cannot maintain codebase quality over time — a training problem no harness engineering can fix. Against this, [Werner Vogels](/reading/2026-06/2026-06-30t173037-a-return-to-two-pizza-culture) argues that AI has compressed prototyping enough to change process: build first, write the spec doc after. The disagreement is not about whether AI belongs in engineering but about where the judgment boundary sits.
