Software engineering is a discipline that has always resisted reduction to a single skill. The sources collected here circle that resistance from many angles: what makes a good engineer, what makes good code, what happens when tooling changes faster than practice, and what gets lost when speed crowds out understanding.

The clearest thread running through the AI-adjacent sources is a distinction between code production and software engineering. [Lars Faye](/reading/2026-04/2026-04-27t145041-agentic-coding-is-a-trap) argues that fully agentic workflows accelerate skill atrophy and invert developer priorities toward speed over comprehension, creating vendor dependency in the process. [Abednego Gomes](/reading/2026-05/2026-05-14t223612-the-perils-of-ai-to-the-software-engineering-profession) sharpens this into a categorical claim: shipping AI-generated code without review is reckless and incompatible with safety-critical systems. [Yusuf Aytas](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter) makes the economic version of the same argument — AI lowers the cost of producing code but not of owning it, and LLMs can generate polished technical debt faster than any individual engineer. The bottleneck, as [The Typical Set](/reading/2026-05/2026-05-06t110728-the-bottleneck-was-never-the-code) puts it, was never the code itself but the organizational clarity required to ship well.

Architectural principles remain contested independent of AI. [Go Monk](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) argues for deep modules — small interfaces hiding large implementations — as the organizing principle for systems readable by both humans and LLMs. [Henrique Teixeira](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) argues that the Single Responsibility Principle is widely misapplied as "do only one thing" when it actually means cohesion under a single accountable responsibility, and that over-granularizing violates the cognitive simplicity SRP exists to provide. [Kobi Hari](/reading/2026-04/2026-04-30t232001-a-better-way-to-build-angular-components-from-inputs-to) applies similar reasoning at the component level, advocating the Composite Components pattern to prevent input-bloated Angular components from becoming maintenance liabilities.

Testing surfaces its own tensions. [The Currents team](/reading/2026-05/2026-05-05t135218-designing-playwright-tests-that-survive-ui-refactors) argues that test suites break during refactors not primarily from bad selector choices but from coupling to implementation details rather than semantic roles. [How To Test Frontend](/reading/2026-06/2026-06-22t185420-code-smells-when-you-get-ai-to-write-your-frontend-tests) documents twenty-plus recurring patterns AI tools introduce when generating frontend tests, including over-mocking, testing only happy paths, and writing tests to match buggy implementations rather than intended behavior. Meanwhile, [Daniel Stenberg](/reading/2026-05/2026-05-02t094735-approaching-zero-bugs) uses curl's vulnerability and bugfix data to argue that despite powerful new AI-assisted static analysis, there is no measurable sign that open-source projects are approaching zero latent bugs.

Institutional knowledge is harder to transfer than codebases. [Cekrem](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you) draws on Michael Polanyi's concept of tacit knowledge to argue that the most valuable engineering expertise — pattern recognition, unwritten conventions, design intuition — is structurally inaccessible to AI tools and can only be transmitted through apprenticeship. [Tuhin Nair](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) locates a related gap in communication: senior engineers frame problems as complexity management while the rest of the business thinks in terms of uncertainty reduction, and bridging that gap is itself an engineering skill. [DHg](/reading/2026-05/2026-05-08t112608-your-onboarding-is-a-hazing-ritual-and-you-call-it-agile) shows what happens when institutional knowledge fails to transfer: onboarding practices disguised as agile process systematically set new hires up to fail.

Practical engineering craft shows up across tooling, version control, and platform choices. [Anton Zaides](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) distills seven production-hardened rules, from rolling back before debugging to treating every external dependency as a future outage. [Ally Piechowski](/reading/2026-06/2026-06-18t024208-the-git-commands-i-run-before-reading-any-code) shows how git log commands can diagnose a codebase's churn hotspots, bus factor, and firefighting frequency before reading a single file. [Ben Gesoff](/reading/2026-05/2026-05-31t164252-reviewing-large-changes-with-jujutsu) describes a Jujutsu-based workflow for reviewing large pull requests that persists progress in version control without the overhead of git stashes.

The field's current debate splits between what [Anton Zaides](/reading/2026-07/2026-07-07t170607-the-software-engineering-war) calls builders and keepers — engineers who prioritize shipping with AI versus those who insist on code quality — with the observation that where you stand depends as much on organizational context as on principle. [Paolo Galeone](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms) argues the resolution requires strong CI/CD, code ownership, and engineering discipline to use AI as an amplifier rather than a replacement for judgment. That framing — judgment as the non-negotiable core — is the one point on which nearly all these sources converge.
