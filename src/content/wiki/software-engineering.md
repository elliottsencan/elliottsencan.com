Software engineering is a practice, not just a collection of techniques. The distinction matters because technique is trainable in isolation while practice requires judgment built through experience, failure, and accumulated context.

A recurring theme across recent writing is the gap between what interviews measure and what production work demands. [Fagner Brack](/reading/2026-04/2026-04-30t155134-learn-algorithms-for-interviews-forget-them-for-work) makes this explicit: algorithm interviews test a narrow, trainable skill that weakly correlates with shipping real systems, which require reading tradeoffs, handling messy inputs, and incrementally delivering value. The same distance between performance-on-benchmark and real-world effectiveness appears in multi-agent evaluation: [Christopher Meiklejohn](/reading/2026-05/2026-05-03t110114-getting-up-to-speed-on-multi-agent-systems-part-7) argues that HumanEval and SWE-bench were built for single-agent measurement and cannot capture coordination quality or failure recovery. Optimizing for a proxy is a persistent failure mode.

Design principles absorb a similar critique. [Henrique Teixeira](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) argues that the Single Responsibility Principle is routinely misread as "do only one thing" when it actually means cohesive grouping under a single axis of change; over-granularizing classes violates the cognitive simplicity SRP is meant to provide. [Go Monk](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) makes a complementary point from the opposite direction: deep modules — small interfaces hiding large implementations — reduce complexity for both humans and LLMs, because the surface the caller must understand stays bounded regardless of interior complexity.

Code quality doesn't become less important when code is cheaper to produce. [Yusuf Aytas](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter) puts it plainly: AI lowers the cost of writing code but not the cost of owning it, and LLMs can generate polished technical debt faster than any human. [Abednego Gomes](/reading/2026-05/2026-05-14t223612-the-perils-of-ai-to-the-software-engineering-profession) is blunter, calling "vibe coding" — shipping AI-generated code without review — categorically incompatible with safety-critical systems. [Paolo Galeone](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms) frames the risk as a "custodian" mindset: engineers shipping code they don't understand, where CI/CD discipline and code ownership are the countermeasures.

The organizational dimension of quality tends to be underweighted. [The Typical Set](/reading/2026-05/2026-05-06t110728-the-bottleneck-was-never-the-code) argues that the bottleneck was never individual code-writing speed but shared context, specification clarity, and management coherence — and coding agents amplify existing alignment or misalignment rather than replacing those fundamentals. [Anton Zaides](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) captures the operational layer: roll back before debugging, treat every external dependency as a future outage, and build on hard-won incident knowledge rather than theoretical best practice.

Skill atrophy is a serious concern across multiple sources. [Lars Faye](/reading/2026-04/2026-04-27t145041-agentic-coding-is-a-trap) argues that full agentic workflows accelerate skill decay and invert developer priorities toward speed over understanding, creating vendor dependency in the process. [Christoph Spörk](/reading/2026-05/2026-05-03t103944-the-lobster-in-the-hot-pot) makes the same argument at an institutional scale: gradual AI dependency erodes organizational knowledge until the cost of running without it becomes prohibitive. [Pete Millspaugh](/reading/2026-05/2026-05-19t193626-slow-mode) proposes a direct countermeasure — a "Slow Mode" agent that keeps the human involved at every step, trading short-term velocity for genuine understanding and long-term code ownership.

Tacit knowledge is the hardest thing to preserve. [cekrem](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you), drawing on Polanyi, argues that pattern recognition, unwritten conventions, and design intuition are structurally inaccessible to AI tools and can only be transmitted through apprenticeship. [Tuhin Nair](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) adds that even within teams, senior engineers communicate in terms of complexity management while the rest of the business thinks in terms of uncertainty reduction — and that gap predates AI.

The tooling layer is evolving fast in ways that cut against complexity. [Sam Alba](/reading/2026-04/2026-04-30t195531-what-ci-actually-looks-like-at-a-100-person-team) describes an AI agent handling CI triage at PostHog's scale — 575K weekly jobs and 33M test executions — tracing flaky tests to root causes and opening fix PRs automatically. [Yaron Minsky](/reading/2026-06/2026-06-15t021106-formal-methods-and-the-future-of-programming) argues that agentic coding has made formal methods newly cost-effective, both by lowering proof-writing costs and by creating demand for verification that goes beyond test coverage. Against this, [Daniel Stenberg](/reading/2026-05/2026-05-02t094735-approaching-zero-bugs) uses curl's vulnerability data to show no measurable sign yet that even powerful AI-assisted static analysis is pushing open-source projects toward zero latent bugs.

Version control practice is undergoing its own evolution. [Ben Gesoff](/reading/2026-05/2026-05-31t164252-reviewing-large-changes-with-jujutsu) documents a workflow for reviewing large pull requests using Jujutsu — inserting an empty parent commit and squashing files into it as review progresses — that makes incremental review state persistent without the overhead of Git stashes. [Dex Horthy](/reading/2026-07/2026-07-23t215330-humanlayeradvanced-context-engineering-for-coding-agents) draws a harder line: "lights-off" software factories fail because LLMs cannot maintain codebase quality over time, a training problem no harness engineering can fix.

The field is split between those who want to ship faster and those who want to ship better, and [Anton Zaides's framing](/reading/2026-07/2026-07-07t170607-the-software-engineering-war) of "builders" versus "keepers" captures the current moment honestly. Both orientations are responding to real pressures. The more durable observation, across almost every source here, is that judgment — about what to build, when to roll back, how to communicate tradeoffs, and when to push back on a tool's output — remains the thing AI cannot yet supply.
