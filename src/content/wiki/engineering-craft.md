Engineering craft is the accumulated set of judgments, habits, and hard-won heuristics that let engineers build systems that hold together over time. It covers everything from how you name a variable to how you structure a team's onboarding, and it resists being fully codified, which is precisely why it keeps being rediscovered.

The tacit dimension is real. [cekrem](/reading/2026-05/2026-05-19t110710-the-tacit-dimension-why-your-best-engineers-cant-tell-you) draws on Polanyi to argue that the most valuable engineering expertise — pattern recognition, design intuition, unwritten conventions — is structurally invisible and can only be transmitted through apprenticeship. [Tuhin Nair](/reading/2026-05/2026-05-13t060018-why-senior-developers-fail-to-communicate-their-expertise) makes a parallel point from a different angle: senior engineers think in terms of complexity management, but the rest of the organization thinks in terms of uncertainty reduction, and the gap between those framings causes much of the miscommunication that passes for incompetence.

The craft shows up in the small decisions. [Matt Smith](/reading/2026-07/2026-07-16t043206-i-stopped-destructuring-everything) argues that reflexive destructuring optimizes for writing code rather than reading it — the object reference carries context that scattered variable names lose. [Fagner Brack](/reading/2026-04/2026-04-30t155134-learn-algorithms-for-interviews-forget-them-for-work) makes a similar point about hiring: algorithm interviews test a narrow, trainable skill that correlates weakly with the real work, which is reading tradeoffs, shipping incrementally, and building systems that handle messy real-world inputs. The tech hiring system, as [Vladimir Klepov](/reading/2026-06/2026-06-22t182141-the-systemic-decay-of-tech-hiring) traces it, has decayed precisely because well-intentioned engineers optimized for process metrics and Goodhart's Law did the rest.

Principles misapplied become anti-craft. [Henrique Teixeira](/reading/2026-06/2026-06-04t073318-single-responsibility-the-distorted-principle) argues that the Single Responsibility Principle is routinely misread as "do only one thing" when it actually means cohesive grouping under a single accountable responsibility — over-granularizing classes violates the cognitive simplicity SRP is meant to provide. [Kobi Hari](/reading/2026-04/2026-04-30t232001-a-better-way-to-build-angular-components-from-inputs-to) applies the same logic to Angular components: a component bloated with dozens of inputs is a failure of encapsulation, not a feature. [Go Monk](/reading/2026-05/2026-05-04t231343-ai-likes-deep-modules) puts it structurally: deep modules — small interfaces hiding large implementations — reduce complexity for both humans and LLMs, where shallow modules spread it.

Craft includes knowing what to build and what not to. [Jim Nielsen](/reading/2026-05/2026-05-05t091632-building-websites-with-llms) argues that replacing JS-powered in-page interactions with separate linked HTML pages is simpler to build and maintain. [Dan Q](/reading/2026-07/2026-07-14t210058-your-app-could-have-been-a-webpage-so-i-fixed-it-for-you) shows the same principle applied: a travel itinerary app delivering plain HTML over HTTP was unnecessary overhead for developers and users alike. Paul Buchheit's older point [still applies](/reading/2026-06/2026-06-22t170134-if-your-product-is-great-it-doesnt-need-to-be-good): great products nail two or three things exceptionally well and deliberately ignore the rest.

At the implementation level, craft means understanding what you ship. [Arthur Pastel](/reading/2026-05/2026-05-14t151252-5-faster-fastblur-in-image-rs) replaced float arithmetic with integer accumulators and costly division with reciprocal multiplication to achieve a 5.9× speedup — a result only reachable by reading the machine, not the API. [Colin McDonnell](/reading/2026-08/2026-08-29t130644-reducing-zods-memory-footprint-by-an-order-of-magnitude) cut Zod's per-schema heap usage up to 10× by replacing eagerly bound methods with lazily memoizing prototype getters. [Marc Brooker](/reading/2026-07/2026-07-19t073255-its-always-tcpnodelay-every-damn-time) documents how Nagle's algorithm, left at its default, silently kills latency in datacenter environments — a reminder that defaults encode assumptions that expire.

The AI question runs through nearly every contemporary discussion of craft. [Yusuf Aytas](/reading/2026-05/2026-05-22t091746-when-code-is-cheap-does-quality-still-matter) identifies the core asymmetry: AI lowers the cost of producing code but not the cost of owning it. LLMs generate polished technical debt faster than any individual engineer. [Abednego Gomes](/reading/2026-05/2026-05-14t223612-the-perils-of-ai-to-the-software-engineering-profession) argues that shipping AI-generated code without review causes skill atrophy and is categorically incompatible with safety-critical systems. [Paolo Galeone](/reading/2026-08/2026-08-05t072544-use-your-brain-engineering-standards-in-the-age-of-llms) calls the failure mode a "custodian" mindset — engineers who ship code they don't understand — and prescribes strong CI/CD and code ownership as the corrective. [Anton Zaides](/reading/2026-08/2026-08-31t131721-the-i-dont-know-claude-wrote-this-pandemic) frames it as cognitive ownership: there is a categorical difference between delegating to AI and blindly accepting its output. [gruhn](/reading/2026-08/2026-08-03t025839-dont-be-a-meat-proxy) names the failure mode directly: relaying raw AI output without validating or synthesizing it shifts the cognitive work onto the recipient.

Craft is also organizational. [Anton Zaides](/reading/2026-06/2026-06-10t073045-the-unwritten-laws-of-software-engineering) distills hard-won production rules — roll back before debugging, treat every external dependency as a future outage — that only accumulate through experience with real systems failing in real ways. [DHg](/reading/2026-05/2026-05-08t112608-your-onboarding-is-a-hazing-ritual-and-you-call-it-agile) argues that poor onboarding disguised as agile process systematically destroys the conditions under which craft can be learned and transmitted. Craft cannot be transmitted where the structure actively prevents it.
